--- title: 'Recent Advances in Software Bug Detection with NLP' date: 2024-12-10 permalink: /posts/2024/12/cybersecurity-nlp/ tags: - Cybersecurity - Natural Language Processing --- Software bug detection can be separated into two kinds of methods: static and dynamic program analysis. Static program analysis scans the source code (or even the object code) of a program for vulnerabilities. Conversely, the technique of dynamic analysis will execute the program. There are many kinds of dynamic analysis, but one of the most common and effective methods is fuzzing.

Fuzzing is a method of finding software vulnerabilities by inputting random or semi-invalid data into a system and monitoring its behavior. Fuzzing originates from 1988-1990 where a Wisconsin graduate level operating systems class created the first black box fuzzing tool which simply used random inputs to test and debug various UNIX utilities. This was incredibly successful, crashing 25-33% of utilities while providing the responsible inputs which allowed rapid bug patching. Since then, fuzzing has become widespread and increasingly sophisticated.

One of the most successful innovations to fuzzing was the 2013 tool, american fuzzy lop (AFL), which uses genetic algorithms to increase test coverage. AFL became ubiquitous because of its performance and easy use. It is primarily a gray-box fuzzer, which has access to an instrumented version of the system being tested and observes the program’s control flow to assess code coverage. The metric of interest to the fuzzer is code coverage, or the percentage of source code being executed during tests. The security engineer using AFL provides several example inputs, which are repeatedly minimized and mutated. There are a series of deterministic mutations, many of which represent edge cases which are often overlooked, and a series of random mutations and splicing that are applied to an input. When a mutated input achieves its goal of executing new parts of the source code, it is added to the queue of useful inputs. More specifically, an input is deemed “interesting” if it yields a unique traversal of the system’s control-flow graph, as measured by the binned hitcounts method. Although AFL provided a testing framework that achieves good code coverage, it was not compatible with continuous integration/deployment.

Several notable projects, such as OSS Fuzz by Google and OneFuzz by Microsoft, integrate fuzzers like AFL, its successor AFL++, libFuzzer, and others, with CI/CD and testing tools with the goal of making software bug detection more accessible. OSS Fuzz was created in 2016, and built upon their 2012 cloud-based tool, ClusterFuzz. Although it is open source, a developer must get their project approved and integrated into OSS Fuzz. OneFuzz was created in 2020 and open source until 2023, whereupon it was archived due to its increased internal use within Microsoft. OneFuzz was self hosted, so anyone could run their suite of desired tests. The primary innovation of these tools was their automatic vulnerability detection as a part of the development pipeline of software.

Today, security researchers are looking for ways to improve the detection of bugs and vulnerabilities in software with the help of natural language processing, as the success and popularity of large language models surges. For example, Google has been exploring how to automatically increase OSS Fuzz’s code coverage with the help of a large language model. On average, OSS Fuzz only touched about 30% of a project’s code, which can be increased by writing more domain/project specific fuzz targets. In an attempt to replace this manual generation of fuzz target code, Google experimented with prompting an LLM to create new targets. The early results, as described in a Google Open Source Security Team blog post in August 2023, were promising (with up to a 29% increase in coverage) and point the organization toward using LLMs to fully automate the creation of fuzz targets, including the initial ones eventually. This would provide all developers easy access to a sophisticated, automatic, easy to use tool for bug and vulnerability detection. Further, large language models could even be used to patch the bugs automatically, with early results revealing a 15% success rate. Ultimately, this method would save an incredible amount of time, but relies on the original principles of fuzzing.

Although fuzzing is an incredibly useful method, this approach of enhancing a fuzzing algorithm with LLM assistance is limited by the capabilities of fuzzing itself. For example, many fuzzers (including AFL) might not be well suited to all languages, such as SQL where most inputs are syntactically invalid. More importantly however, after decades of this methodology’s ubiquity, researchers have found diminishing returns. For example, fuzzing struggles to identify variants of previously patched vulnerabilities, which is where attackers seem to be focusing their efforts recently. This could be because code coverage is less important than finding the right input for these kinds of problems. Luckily, the task of finding variants of previous vulnerabilities is well suited to today’s LLMs, because information about the previously fixed bug provides useful context as a starting point.

Google’s Project Zero and Deepmind have created a new team Big Sleep (evolved from Naptime) which quickly found success in using LLMs to find a vulnerability in the SQLite repository. Along with the other necessary components for the Naptime architecture, they provided Gemini 1.5 Pro with the commit message and diffs of several recent commits to the repository. Through a chain of reasoning and interaction between the LLM agent and the program, it was able to identify the vulnerability and the kind of input necessary to exploit it. The team notes that they could not identify the SQLite stack underflow vulnerability with an AFL fuzzer until they provided a nearly crashing initial input. One of the advantages of this architecture is the combination of static and dynamic analysis, wherein the LLM agent might be able to find issues that fuzzing can’t as a result of code analysis. This is only possible because the LLM has a complex understanding of the code and project. Another useful aspect of this approach is the detailed thought process and analysis provided by the language model, which makes patching the bugs that it finds much faster and easier. Although the early results are promising, the Big Sleep team remains skeptical of its future, as these LLM models don’t seem to be as revolutionary to defense research as fuzzing and AFL were.

Another tool, Vulnhuntr by Protect AI, has found success in a purely static analysis of python code using Claude 3.5. The main obstacle Vulnhuntr overcomes is the small context size available for use in most LLMs. Thus, with careful prompting, the tool analyzes the entire call chain through a series of requests and chain of thought reasoning to find vulnerabilities. They quickly found over a dozen zero-day vulnerabilities in large, popular github projects. This is impressive and promising, but there are still many limitations to the tool. Although the team attempted to improve their model with retrieval-augmented generation or finetuning to better analyze a codebase and create the vulnerability call chain, they only found success with a static parser (specifically Jedi). This is especially difficult/problematic for dynamically typed languages, such as python, thus limiting the model’s performance. As the size of valid context windows increases, static code analysis like that of Vulnhuntr should prove increasingly useful to defense. The Vulnhuntr team notes, however, that even with an infinitely large context window, the static parsing and call chain analysis probably assists the LLM in analyzing the code and identifying vulnerabilities.

Ultimately, the main innovations of Big Sleep and Vulnhuntr is to leverage a large language model’s complex semantic understanding of code. This was not previously possible, as most previous popular methods of bug detection relied on a purely dynamic analysis of a system based on its behavior given specific inputs/circumstances. These models have a sophisticated understanding of code, which, along with complex reasoning, gives them the capacity to perform or assist humans in high level security analysis. Although the early results are not as groundbreaking as previous innovations in the field, there is room for these tools in the future of security engineering, especially as large language models get even better and attackers use similarly more sophisticated tools. Many of the current shortcomings of these tools might be resolved in the future with the creation of better base LLM models, possible finetuning, improved prompt engineering, and an integration between static and dynamic tools or between human and machine agents.
